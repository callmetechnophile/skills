# V0.3 Rust Security Architecture & Threat Mitigation Model

## 1. Threat Model & Trust Boundaries

The V0.3 Rust architecture enforces strict security boundaries around agent skills, which are inherently untrusted instructions and executable payloads:

```text
[ UNTRUSTED INPUT ] ---> [ STATIC SCANNER ] ---> [ TRUST POLICY ] ---> [ ACTIVATION ENGINE ] ---> [ AGENT WORKSPACE ]
  (SkillsDirectory /       (Linear Regex /         (State Machine:       (SHA-256 Hash           (OS Sandbox /
   GitHub Upstream)         AST Tokenizer)          APPROVED/RESTRICTED)  Verification)           Runtime Bridge)
```

### Attack Vectors Mitigated:
1. **Prompt Injection & Instruction Overrides:** Patterns attempting to hijack agent identity (`ignore previous instructions`, `unrestricted mode`, `DAN mode`).
2. **Credential Exfiltration:** Shell or network payloads targeting `.env`, SSH keys, AWS credentials, or piping secrets to external webhooks.
3. **Destructive Filesystem Commands:** Commands deleting critical paths (`rm -rf /`, `rmdir /s /q c:\`, formatting drives).
4. **Obfuscation & Dynamic Code Execution:** Base64 decoding, hex payloads, and shell piping (`curl ... | bash`).
5. **Silent Local Tampering:** Upstream updates attempting to silently overwrite modified local workspace files.

## 2. Rust Security Subsystem Design (`skill-security`)

### 2.1 Static Scanner Engine
- Uses the `regex` crate which guarantees $O(n)$ matching time with zero vulnerability to Regular Expression Denial of Service (ReDoS).
- Inspects `SKILL.md`, shell scripts, Python files, and dependency commands.
- Calculates cryptographic SHA-256 hashes using the `sha2` crate.
- Never executes any script during scanning or discovery.

### 2.2 Trust State Machine
```text
                  +------------+
                  | UNSCANNED  |
                  +-----+------+
                        |
                        v
                  +------------+
                  |  SCANNING  |
                  +-----+------+
                        |
         +--------------+--------------+--------------+
         |                             |              |
         v                             v              v
   +----------+                  +------------+ +----------+
   | APPROVED |                  | RESTRICTED | | REJECTED |
   +----------+                  +-----+------+ +----------+
                                       |
                              (Requires Human
                                 Approval)
```
- **APPROVED:** Zero rule violations detected.
- **RESTRICTED:** Potentially sensitive operations (listening network sockets, external APIs). Requires explicit `--approve-restricted` flag.
- **QUARANTINED:** Obfuscated or base64 command execution. Activation blocked.
- **REJECTED:** Critical security threat (exfiltration, override, destructive command). Activation unconditionally blocked.

### 2.3 Secret Leak Prevention in Tracing & Logs
- All logging via `tracing` strictly redacts environment variables matching `*KEY*`, `*SECRET*`, `*TOKEN*`, `*PASSWORD*`, `*AUTH*`.
- Structured error types (`thiserror`) sanitize file paths and reject embedding raw secret values into error strings.

## 3. Sandboxing & Operational Boundaries

> [!IMPORTANT]
> **Static Scanning Limitation:** Static analysis is an essential line of defense but cannot mathematically guarantee safety against novel semantic prompt injections.
> **OS Sandboxing:** The Skill Router does **not** implement a custom operating-system sandbox. Real code execution sandboxing must be enforced by host agent containerization (e.g. Docker, Podman, gVisor, or macOS Sandbox / Windows Job Objects) at the runtime layer.
